## QA-5 — i18n gaps across visitor surface + auth + dashboard titles + need a tool to find them

**Status**: OPEN
**Resolved by**: —
**Prior history**: B.PT26 + B.PT26B shipped i18n for the date
formatters, auth pages, loading skeletons, and the availability-
field chrome (modal title, buttons, error messages, day-name range
compression). The user is now reporting that significant
additional surface area is still rendering English strings even
when the locale is `es` — most notably the `/h/<handle>` "Pick a
date" trigger + booking form, the `/login` form's `name` / `email`
field labels + chrome, and most page / dashboard titles. They want
both the specific fixes AND a tool that finds every i18n gap
automatically so manual hunt-and-peck stops.

**Symptom (sub-issue A — specific gaps)**: At least three confirmed
surfaces still render hardcoded English when the user's locale is
`es`:
- `/h/<handle>`: "Pick a date" trigger + the booking form fields /
  labels.
- `/login`: form field labels (`name`, `email`) + button titles +
  related chrome.
- Multiple page titles + dashboard section titles across `(host)/`
  routes — listed by the user as "most of the things aren't
  translated."

**Symptom (sub-issue B — coverage tooling)**: User wants a TOOL or
contract test that catches every untranslated user-visible string
in the app at `pnpm test:run` time, so the next time someone adds
a new screen they can't ship a hardcoded English label without CI
noticing. Manual walkthrough is not sustainable.

**User note**:

> The pick a date and the picking a date form don't have the i18n
> translation either it all has the page except for that what's
> causing it and how can we fix it and what can we do to check
> everywhere in the oro Project where i18n should be that we make
> sure it is in fact there not just by manually finding out that
> is not translating at all. Also it happens in the login form
> that it sort of works but things like the "name" or "email"
> things in the buttons like titles and stuff don't work so if
> possible I think whatever we do in order to check everywhere as
> I said before should also catch this type of cases too. I just
> did step 8 and I notice like in a lot of places in the app most
> of the things aren't translated like the titles of the pages
> and the dashboard titles either so whatever we do or tool we
> use must find all this cases the translation in availability
> works tho for the form itself not its page title or anything at
> all

**Open questions**:
- (Sub-A) The `/h/<handle>` page is `host-profile.tsx` — it
  already imports `useTranslations` (per B.PT26's date formatter
  swap). Does it use translations for slot-picker copy too?
  Search the file for hardcoded English strings.
- (Sub-A) `/login` mostly translated post-B.PT26 but the user
  reports gaps in field labels and buttons. The fields are
  rendered by `CredentialsForm` and `MagicLinkForm` — neither
  was touched by B.PT26 (only the page shell was). Need to apply
  the same `Auth` namespace to those sub-forms.
- (Sub-A) Page titles + dashboard section titles — these likely
  live in `OhPageHeader` instances + section legends across the
  `(host)/` route group. Each call site passes a literal string
  today; need to thread `t("…")` per route.
- (Sub-B) What's the canonical pattern for an i18n-coverage
  contract test? Options:
  - **AST-based**: parse every `*.tsx` under `src/app` with
    `@babel/parser`, find JSX text nodes that aren't `{...}`
    expressions, exclude allow-listed identifiers (mono numbers,
    SVGs, etc.). Fail with file:line listings.
  - **Regex-based**: walk every `*.tsx` line, find any text
    inside `>...<` that isn't `{...}`, isn't whitespace, and
    contains alphabetic chars. Fast but more false positives.
  - **next-intl runtime check**: run `pnpm dev` + Playwright,
    crawl every route in both `en` and `es` locales, diff the
    rendered HTML — any text identical between locales is
    candidate untranslated. Heaviest but most accurate.
- (Sub-B) Cal.com / dub coverage test reference — do they have
  one? cal.com has 100+ locales and is the canonical reference
  for i18n discipline at scale.

**Research vector**:
- (Sub-A) `src/app/h/[handle]/components/host-profile.tsx` — every
  `<button>`, `<TriggerCard>` label, drawer title. Confirm what's
  translated vs not.
- (Sub-A) `src/components/calendar/AvailabilityDrawer.tsx`,
  `BookingDrawer.tsx`, `TriggerCard.tsx` — this is where most of
  the visitor booking form copy actually lives (called by host-
  profile).
- (Sub-A) `src/app/login/credentials-form.tsx` +
  `src/app/login/magic-link-form.tsx` — auth form sub-components.
- (Sub-A) `src/components/oh/page-header.tsx` + every consumer
  under `src/app/(host)/` — page-title sweep.
- (Sub-A) `src/components/oh/section-header.tsx` consumers — the
  `legend` prop is a literal English string in most of them.
- (Sub-B) `src/lib/__tests__/no-mid-dot.test.ts` (B.PT27) +
  `src/lib/__tests__/i18n-no-duplicate-keys.test.ts` (B.PT90) —
  these are the existing pattern references for "vitest contract
  that walks the source tree." Same shape works for an i18n
  coverage check.
- (Sub-B) Cal.com `packages/lib/i18n.ts` + their i18n test
  pipeline — `find ~/Desktop/cal.com -name "*.test.ts" -path
  "*i18n*"`.
- (Sub-B) `next-intl` docs (Context7 `/next-intl/docs`) — they
  have official patterns for missing-key detection and an
  optional dev-only `getMessageFallback` that throws on missing

**Acceptance criteria**:
- Sub-A — Three concrete sweeps shipped as separate `B.PT##`
  commits (one per surface family): visitor booking flow,
