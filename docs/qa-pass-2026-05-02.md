## QA-1 — Workspace rename + browser back → 404

**Status**: FIXED
**Resolved by**: B.PT82

**Symptom**: After renaming a workspace from its detail page (and
therefore changing its slug), pressing the browser back button lands on
the old slug URL, which returns `notFound()`. Mechanically expected
(slug changed → old URL is gone), but UX-wise it surprises the user.

**User note**:

> When renaming a workspace and coming from the detail page if you
> press back it says not found because we just renamed it and it
> makes sense but shouldn't we instead check sequentially how dub or
> cal codebases handle it instead perhaps we could just use some sort
> of id or something similar. Make sure you use all of your tools and
> never skip there is no time limit.

**Open questions**:
- Do dub / cal route by **stable ID** (cuid / numeric) instead of slug?
  If so, slug rename never invalidates a URL.
- If they keep slug-based routing, do they redirect old slug → new slug
  via a server-side lookup table or an `OldWorkspaceSlug` model?
- Or do they `replaceState()` the new URL on rename so back-stack never
  contains the old slug?

**Research vector**:
- `~/Desktop/cal.com/apps/web/app/team/[orgSlug]/...` — team rename flow
  + post-rename navigation.
- `~/Desktop/dub/apps/web/app/[workspace]/...` — slug change handling.
- Schema audit: does the lab need an `OldWorkspaceSlug` model, or
  switch routing to ID + render slug as a display-only field?

**Acceptance criteria**: After renaming `acme` → `acme-inc`, browser
back from `/workspaces/acme-inc/settings` does NOT 404. Either lands on
the new slug, or shows a redirect-with-toast, or any other path the
reference codebases endorse.

**Open questions**:
- What's the canonical pattern for edge-case discovery in TRPC + Prisma
  apps? Options:
  - **Property-based testing** (`fast-check` + Vitest) — generate
    inputs, assert invariants survive.
  - **Mutation testing** (`stryker-mutator`) — flip operators, see
    which tests catch the regression.
  - **Playwright invariant flows** — multi-step E2E that asserts
    cross-cutting properties (e.g., "after a workspace rename, no
    stale URL responds with 200").
  - **State-machine fuzzing** of booking lifecycle.
- How do cal.com / dub structure their edge-case test suites? Test
  files named `*.invariants.test.ts` exist in either repo?

  — booking edge-case tests.

- Context7: `fast-check` (property-based) + `stryker-mutator` (mutation
  testing) docs.

**Acceptance criteria**: A documented playbook (likely a new
`docs/edge-case-testing.md`) that lists the patterns adopted, with
a reference test for each pattern wired into the project's CI gates.
Not necessarily a full suite — a foundation to build on per item as
fixes land.
